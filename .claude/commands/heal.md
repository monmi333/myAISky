myAISky 자율 운영 루프를 실행한다. 사용자가 준 증상(선택): $ARGUMENTS

세 서브 에이전트를 **순서대로** 호출한다. 앞 단계의 결과가 다음 단계의 입력이다. 병렬로 실행하지 않는다.

## 0. 사전 확인

- `curl -s -o /dev/null -w "%{http_code}" localhost:8000/` 로 서버가 떠 있는지 확인한다.
- 서버가 떠 있지 않으면 중단하지 말고 다음 단계를 진행한다. 다만 ops-monitor 결과에 "서버 다운"으로 기록되고, 배포 단계의 기동 테스트는 임시 포트로 따로 수행된다.
- 사용자가 `$ARGUMENTS` 로 증상을 줬다면 그 내용을 1단계 입력에 포함한다.

## 1단계: weather-healer (진단·치유)

`weather-healer` 에이전트를 호출한다. 전달 내용은 다음과 같다.

- 증상(`$ARGUMENTS`가 있을 때)
- 지시: 최근 로그에서 WARN/ERROR와 API 403, 파싱, DB 적재 실패를 찾아 진단하고, 원인이 확인되면 `backend/main.py` 를 최소 범위로 수정한다. 수정·검증은 최대 2회다.
- 제약: `.env`, `weather_logs.db` 수정 금지. 커밋·푸시 금지.

결과 중 **수정한 파일과 미해결 사유**를 기억해 둔다. 수정이 없고 장애도 없으면 그대로 다음 단계로 간다.

## 2단계: ops-monitor (생존·DB 점검)

`ops-monitor` 에이전트를 호출한다. 1단계에서 수정이 있었다면 "수정 후 상태"를 점검하도록 명시한다.

점검 결과 판정을 기억한다.

- **장애**: 서버 다운, 수집 공백, DB 정체. 3단계로 가기 전에 1단계를 한 번 더 호출할지 판단한다. 같은 원인을 두 번 고치려 하지 않는다. 두 번째에도 장애라면 3단계는 진행하되, 배포 내용을 "장애 상태에서의 수정"으로 명시한다.
- **정상 또는 주의**: 3단계로 간다.

## 3단계: deploy-guardian (테스트·커밋·푸시)

`deploy-guardian` 에이전트를 호출한다. 전달 내용은 다음과 같다.

- 1단계에서 수정된 파일 목록과 수정 요지(없으면 "변경 없음")
- 2단계 판정 요약
- 지시: 테스트 게이트를 통과한 변경만 커밋하고 현재 feature 브랜치에 푸시한다. `main` 에 직접 푸시하지 않는다. `.env`, `*.db`, `carMaintenance/` 는 제외한다.

**커밋할 변경이 없으면** 푸시는 생략하고 "변경 없음"으로 끝난다. 이것은 실패가 아니다.

**테스트나 비밀정보 검사가 실패하면** 푸시하지 않는다. 사용자에게 실패 사유를 보고하고 멈춘다.

## 최종 보고

세 단계 결과를 한 번에 정리한다.

```
[1. weather-healer] 장애: ... / 수정: 파일:라인 또는 없음 / 미해결: ...
[2. ops-monitor]    판정: 정상|주의|장애 / DB total N / 마지막 수집 ...
[3. deploy-guardian] 판정: 배포 완료|보류|차단|변경 없음 / 커밋 해시 / 푸시 브랜치
사용자 조치: (예: 인증키 확인, 서버 재기동)
```

- 실제로 수행한 단계만 "완료"라고 쓴다. 건너뛴 단계는 이유와 함께 "생략"으로 적는다.
- 사용자가 직접 해야 할 일(인증키 재발급, 서버 재기동 등)은 빠뜨리지 않는다.
- 이 명령은 커밋과 푸시를 포함하지만, 그 전에 테스트 게이트를 거치므로 검증되지 않은 코드는 올라가지 않는다.

## 주기 실행

이 명령을 10분마다 자동으로 돌리려면 사용자가 `/loop 10m /heal` 로 설정해야 한다. 이 파일 자체는 주기 실행을 설정하지 않는다.
